# Balalaika multi-node: архитектура и план реализации

**Статус:** исследование завершено; дополнительный SSH/rsync controller,
Docker/direct runtime, multi-GPU mapping, dashboard stop/drain, глобальные
WebDataset shard ranks и dataset finalizer реализованы. Первый пилот предполагает,
что pipeline, venv, models и rsync уже подготовлены на worker-нодах; обычный
`base.sh` остаётся независимым от controller.

**Последнее обновление:** 2026-08-09

**Рабочая ветка:** `feat/multinode-docker`

## Краткое резюме

Balalaika можно запускать на нескольких GPU-нодах. Для этого не нужны DDP,
NCCL или разделение одной модели между машинами. Аудиоэлементы независимы,
поэтому это задача распределённой пакетной обработки.

Небезопасно независимо запускать текущий `base.sh` на нескольких нодах с одним
общим каталогом датасета, доступным для записи. Могут конфликтовать подготовка
очереди, файлы частичных результатов, агрегация Parquet, обновления JSON, файлы состояния,
деструктивные фильтры и имена экспортных шардов.

Предлагается следующая архитектура:

1. Nomad планирует запуск закреплённых Docker-образов и резервирует NVIDIA GPU.
2. Небольшой Balalaika Coordinator управляет запусками, манифестами партиций,
   leases, retries, политикой стадий и финальной публикацией.
3. Датасет делится на множество неизменяемых партиций, сбалансированных по
   вычислительной стоимости.
4. Worker размещает одну партицию на локальном SSD/NVMe ноды, запускает
   существующий pipeline с изолированным `podcasts_path` и загружает проверенные
   результаты.
5. Объектное хранилище используется как надёжный холодный уровень, а не как
   файловая система для каждого чтения аудио. Критический путь остаётся локальным для
   каждой ноды.
6. Модели и движки TensorRT постоянно кэшируются на каждой ноде: weights
   скачиваются один раз на ноду и затем читаются из локального cache.

Эта схема оставляет без изменений большую часть кода модельных стадий и не
превращает единственный HDFS/NFS-сервер в узкое место инференса.

## Цели

- Управлять пулом из 2-10 bare-metal GPU-нод из одной точки.
- Явно задавать уже подготовленные pipeline, venv, models и cache пути каждой
  ноды без скрытых host/container предположений.
- Использовать внутри каждого контейнера только явно выделенные GPU.
- Динамически балансировать разнородное аудио между разнородными нодами.
- Не читать удалённо миллионы мелких аудиофайлов при каждом проходе.
- Возобновлять работу после сбоя процесса, контейнера, ноды или сети.
- Сохранять воспроизводимость при повторных попытках и изменении числа нод.
- Сохранить текущую последовательную семантику стадий и межстадийные барьеры.

## Не является целью

- Распределённое обучение.
- Разделение одной модели инференса между несколькими нодами.
- Одновременная запись нескольких стадий в одну партицию.
- Использование HDFS, S3 или FUSE как прямой замены POSIX-файловой системы для
  текущего pipeline.
- Переписывание всех стадий под Audiogear API.

## Как работает текущий конвейер

[`base.sh`](../base.sh) является оркестратором для одной машины. Он запускает по
одному Python-процессу на стадию и последовательно переходит к следующей.
Стадии взаимодействуют только через файлы:

- дерево аудиодатасета;
- один файл состояния `balalaika.parquet`;
- один сопутствующий JSON-файл на каждый аудиочанк;
- временные частичные CSV и work-shard-файлы;
- файлы состояния и аудита стадий.

Это явно описано в [`CLAUDE.md`](../CLAUDE.md#L61-L71). Граница в виде файловой
системы упрощает возобновление, но одновременно означает, что сейчас файловая система
выполняет роль слоя транзакций и координации.

### Текущий параллелизм стадий

| Стадии | Текущее поведение | Следствие для multi-node |
|---|---|---|
| 0 | Загрузка/ingest | Оставить на стороне controller или подготовить неизменяемые входы до запуска. |
| 1 raw | Родительский процесс делит источники между локальными GPU | Должна выполняться внутри одной изолированной партиции; сейчас это не кластерная очередь. |
| 1 existing chunks | Использует дисковые work shards | Можно повторно использовать внутри партиции. |
| 2, 3, 3.5 | Дисковые work shards/локальные GPU workers | Можно повторно использовать внутри партиции. |
| 4, 5, 6, 7 | Scoring-стадии, в основном с дисковыми work shards | Подходящие стадии для пилота. |
| 4.5, 5.5, 6.5, 7.5 | Деструктивные фильтры | Безопасны только в одноразовом workspace партиции, пока не реализована двухфазная фильтрация. |
| 8 | Multi-model ASR и ROVER, дисковые work shards | Дорогая стадия, подходящая для распределения на уровне партиций. |
| 9, 10, 11 | Материализуют списки pending-элементов в локальные pools | Сначала выполнять локально внутри партиции; менять только при необходимости. |
| 12 | Denoising на основе очереди, перезаписывает аудио | До мелкогранулярных retries нужна атомарная публикация медиафайлов. |
| 12.5 | Повторная проверка после denoising на основе очереди | Можно повторно использовать внутри партиции. |
| 13 | Единственный Parquet writer | Выполнять один раз на партицию; кластерный finalizer объединяет манифесты/фрагменты. |
| 14 | Локальный process pool и локальные имена worker shards | Выполнять для каждой партиции с отдельным namespace результатов. |
| 15 | Единственный report writer | Формировать сводки партиций, затем один агрегированный отчёт уровня кластера. |

## Почему несколько текущих процессов `base.sh` небезопасны

Ниже перечислены проблемы корректности, а не только ограничения
производительности.

1. При подготовке очереди перед записью новых шардов удаляется весь рабочий
   каталог стадии. Второй planner может удалить pending- или running-работу
   другой ноды:
   [`src/utils/work_shards.py`](../src/utils/work_shards.py#L71-L79).
2. Имена файлов частичных результатов содержат только локальный rank. На каждой
   ноде есть rank 0, rank 1 и так далее, поэтому имена конфликтуют:
   [`src/utils/csv_manager.py`](../src/utils/csv_manager.py#L952-L960).
3. `absorb_partial_csvs` объединяет и затем удаляет совпадающие partial-файлы.
   Merger может удалить файл, пока другая нода продолжает добавлять в него
   строки:
   [`src/utils/csv_manager.py`](../src/utils/csv_manager.py#L1011-L1041).
4. При публикации chunk JSON используется временный файл с последующим rename,
   но цикл read-modify-write не защищён распределённой блокировкой. Корректность
   предполагает последовательные стадии и непересекающееся владение
   элементами:
   [`src/utils/chunk_json.py`](../src/utils/chunk_json.py#L28-L32).
5. Каждая нода будет записывать один и тот же `stage_<id>_status.json`:
   [`src/utils/stage_status.py`](../src/utils/stage_status.py#L27-L61).
6. Добавление audit-записей не координируется между нодами:
   [`src/utils/audit.py`](../src/utils/audit.py#L42-L80).
7. Denoising сохраняет результат непосредственно поверх исходного аудио.
   Прерванный процесс кодирования может оставить повреждённый файл без завершённого
   обновления состояния:
   [`src/denoising/denoising.py`](../src/denoising/denoising.py#L208-L224).
8. Collate открывает канонический Parquet-файл результата напрямую. При сбое
   частичный файл может стать видимым:
   [`src/collate.py`](../src/collate.py#L285-L364).
9. При каждом запуске WebDataset начинает нумерацию workers с нуля, поэтому
   несколько нод используют один namespace шардов:
   [`src/to_webdataset.py`](../src/to_webdataset.py#L206-L230).
10. Сейчас в состоянии хранятся абсолютные пути к файлам. Результаты с разных
    локальных mount points нельзя переносимо объединить:
    [`src/utils/csv_manager.py`](../src/utils/csv_manager.py#L105-L122).
11. Имена TensorRT cache содержат только локальный CUDA index. Два хоста с
    общим cache могут конфликтовать, даже если их GPU различаются:
    [`src/utils/gpu.py`](../src/utils/gpu.py#L126-L157).

`fcntl.flock` и атомарный rename помогают в пределах одной локальной
POSIX-файловой системы. Они не являются полноценным протоколом распределённой
координации, и нельзя полагаться на их поведение в object/FUSE storage.

## Результаты исследования Audiogear

Указанный проект был изучен на commit
[`07f5b240`](https://github.com/lIkesimba9/audiogear/tree/07f5b240eb0a413e649e7a4e13930cf31f5c85a6).
В рамках этого исследования его облегчённый набор тестов завершился с
результатом 73 passed и 3 skipped. Проект полезен как ориентир, но не является
полноценным кластерным планировщиком.

Multi-node-поведение Audiogear представляет собой статический data parallelism:

- топология определяется переменными окружения, например node rank и node count;
- глобальное число ranks делится на фиксированные диапазоны по нодам;
- локальные процессы закрепляются за GPU;
- каждый rank записывает отдельный результат и completion marker;
- JSONL checkpoints позволяют rank пропускать завершённые элементы после restart.

Значимые части реализации:

- [руководство по multi-node](https://github.com/lIkesimba9/audiogear/blob/07f5b240eb0a413e649e7a4e13930cf31f5c85a6/docs/multi-node.md)
- [топология и диапазоны ranks](https://github.com/lIkesimba9/audiogear/blob/07f5b240eb0a413e649e7a4e13930cf31f5c85a6/src/audiogear/build.py#L63-L98)
- [локальный executor и закрепление GPU](https://github.com/lIkesimba9/audiogear/blob/07f5b240eb0a413e649e7a4e13930cf31f5c85a6/src/audiogear/executer/local.py#L14-L150)
- [completion markers](https://github.com/lIkesimba9/audiogear/blob/07f5b240eb0a413e649e7a4e13930cf31f5c85a6/src/audiogear/executer/base.py#L54-L129)
- [checkpoints для отдельных ranks](https://github.com/lIkesimba9/audiogear/blob/07f5b240eb0a413e649e7a4e13930cf31f5c85a6/src/audiogear/pipeline/checkpoint.py)

В нём нет атомарного claim задач, leases, heartbeat, work stealing,
автоматического failover, хешей config/model/input в completion markers или
общекластерного completeness barrier. Статические ranks также хуже динамической
очереди балансируют аудио переменной длительности. Каждый CSV rank сканирует
общий вход с метаданными, умножая I/O метаданных.

Следует переиспользовать следующие идеи:

- обнаружение топологии;
- явное ограничение видимости GPU до инициализации CUDA;
- глобально уникальные namespaces результатов;
- completion markers и append-only checkpoints.

Не следует устанавливать Audiogear как runtime-зависимость или переносить под
него весь pipeline. Его текущее ограничение требует более старую версию PyTorch,
чем закреплённое окружение Balalaika с PyTorch 2.8, а перенос потребует масштабного переписывания,
не добавляя отсутствующую семантику обработки сбоев.

## Рассмотренные альтернативы

### Одна общая POSIX-файловая система и очередь на всю стадию

Один leader мог бы готовить каждую стадию, а workers со всех нод могли бы
забирать общие pending shards. Это наименьшее концептуальное расширение
текущего механизма `work_shards`.

Даже в этом случае нужны namespaces очередей, блокировка planner, глобально
уникальные partial-файлы, leases, единственный writer состояния, кластерные
barriers и проверенное поведение rename/lock в NFS/Lustre/CephFS. Кроме того,
повторные чтения аудио и операции с метаданными приходятся на общее хранилище.
Такой режим остаётся полезным там, где уже есть быстрая общая система хранения,
но он не отвечает цели убрать центральный I/O hot path.

### Статические ranks в стиле Audiogear

Такой прототип можно сделать быстро, но он имеет слабую балансировку нагрузки и
требует ручного восстановления. При изменении числа ranks меняется владение
данными. Подход допустим для контролируемого теста производительности, но не является
предпочтительной production-архитектурой.

### Kubernetes Jobs

Kubernetes предоставляет зрелые параллельные Jobs и семантику retry. Это
подходящий вариант, если Kubernetes-кластер уже существует. Для отдельного
bare-metal-развёртывания на 2-10 нод он добавляет больше инфраструктуры, чем
требуется, при этом locality данных, семантика стадий Balalaika и публикация
результатов всё равно требуют собственной логики. См. официальную
[документацию Kubernetes Job](https://kubernetes.io/docs/concepts/workloads/controllers/job/).

### Slurm

Slurm job arrays, GPU GRES, dependencies и requeue хорошо соответствуют этой
нагрузке, если кластер уже работает под управлением Slurm. Устанавливать его
только ради Balalaika сейчас не является первым выбором.

### Собственный controller и прямые Docker agents

Это уменьшает число сторонних компонентов, но возлагает на Balalaika
ответственность за безопасность Docker API, блокировку GPU, обновление agents,
состояние нод, placement и перезапуск контейнеров. Собственная логика будет
ограничена семантикой pipeline, а для жизненного цикла машин и ресурсов будет
использоваться Nomad.

## Выбранный уровень управления (control plane)

### Компоненты

```text
                         small metadata traffic
  Operator/UI  --->  Balalaika Coordinator  --->  PostgreSQL
                            |
                            | submit/poll batch workers
                            v
                      Nomad servers
                     /      |       \
              Nomad client  ...   Nomad client
              Docker + GPU        Docker + GPU
                    |                  |
              local partition    local partition
                    \                  /
                     object storage
                stage-in / stage-out only
```

Nomad отвечает за:

- членство и состояние нод;
- placement Docker-контейнеров;
- резервирование CPU, RAM и GPU;
- политику restart/reschedule;
- логи и жизненный цикл каждой allocation.

Coordinator отвечает за:

- манифесты датасетов и запусков;
- очередь и приоритет партиций;
- состояние lease/heartbeat/fencing;
- разрешённые диапазоны стадий и barriers между ними;
- идентификаторы input/config/image/model;
- решения о retries с учётом семантики;
- валидацию и финальную публикацию датасета.

У Nomad есть официальный NVIDIA device plugin, который предоставляет выбранные
устройства Docker allocations, а batch allocations поддерживают политики
restart/reschedule:

- [NVIDIA GPU device plugin для Nomad](https://developer.hashicorp.com/nomad/plugins/devices/nvidia)
- [batch schedulers в Nomad](https://developer.hashicorp.com/nomad/docs/concepts/scheduling/schedulers)
- [политика reschedule в Nomad](https://developer.hashicorp.com/nomad/docs/job-specification/reschedule)

Для первого пилота на двух нодах допустимы один сервер Nomad и одна база данных
Coordinator. В production HA следует использовать три сервера Nomad и
PostgreSQL с резервным копированием. Блокировка строк PostgreSQL, включая
`SKIP LOCKED`, подходит для небольшой очереди задач, однако leases и fencing
tokens всё равно необходимы:
[условие блокировки PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE).

### Модель allocation для worker

Безопасная начальная единица:

```text
one allocation = one writable partition root = all GPUs reserved for that node
```

Это соответствует текущему предположению, что один `base.sh` владеет корнем
датасета и запускает по одному локальному процессу на каждый видимый GPU. На
нодах с SSD/NVMe позднее можно запускать по одному контейнеру на GPU, но только
если каждый контейнер владеет отдельной партицией. На единственном HDD несколько
независимых контейнеров, скорее всего, создадут конкурирующие случайные чтения,
поэтому предпочтительна одна allocation на ноду.

Разнородные ноды группируются в hardware classes, например `a100x8` и
`rtx6000ada4`. Каждый класс получает собственный batch/node profile. Динамические
leases партиций позволяют быстрым нодам завершать больше партиций без изменения
правил владения результатами.

## Локальный для партиций уровень данных (data plane)

### Определение партиции

Партиция является самодостаточным неизменяемым входом для scheduler. Она
содержит набор исходных записей или предварительно нарезанного аудио и манифест
файлов. Все данные, производные от одной исходной записи, остаются в одной
партиции.

Партиции балансируются по оценочной стоимости обработки, прежде всего по
суммарной длительности аудио и набору стадий, а не по числу файлов. Сначала
следует создать в 4-10 раз больше партиций, чем активных нод, а затем настроить
их размер по результатам измерения загрузки моделей, передачи данных, retry и
tail latency. Партиции должны быть достаточно крупными, чтобы амортизировать
запуск моделей, но достаточно небольшими, чтобы сбой ноды не отбрасывал много
часов работы.

Манифест Coordinator содержит как минимум:

```text
partition_id, input_uri, input_sha256, input_bytes, audio_seconds,
run_id, image_digest, config_digest, model_manifest_digest,
state, owner_node, lease_epoch, lease_until, attempt_id
```

### Поток обработки

1. Coordinator создаёт манифест запуска и множество queued-партиций.
2. Worker allocation получает lease на следующую подходящую партицию.
3. Если партиция уже закэширована на этой ноде, ей отдаётся предпочтение по
   locality.
4. Worker загружает один неизменяемый архив в `*.partial` на локальном диске.
5. Он проверяет checksums и атомарно переименовывает/распаковывает размещённый
   вход.
6. Docker-контейнер запускает выбранные стадии Balalaika с этим локальным корнем
   партиции. Переиспользуются существующие локальные `work_shards`, sidecars и
   логика resume.
7. Worker проверяет число строк, status стадий, хеши файлов и схему результатов.
8. Он загружает результаты в неизменяемый prefix, отдельный для attempt.
9. Он последним записывает `_SUCCESS` и выполняет commit с текущим
   lease/fencing token.
10. Coordinator назначает следующую партицию освободившейся allocation.

Controller никогда не проксирует аудио. Аудио передаётся один раз на stage-in,
а затем многократно читается с локального диска ноды.

### Надёжное хранилище

Используйте S3, MinIO или Ceph object storage как холодный источник истины. Не
монтируйте его как `podcasts_path`. Объединяйте мелкие файлы в средние/крупные
неизменяемые архивы, например `tar.zst`, с отдельным манифестом файлов и
checksums, чтобы stage-in не выполнял миллионы мелких object GETs.

Пример layout:

```text
s3://<bucket>/balalaika/
  datasets/<dataset_id>/partitions/<partition_id>/
    input.tar.zst
    input.manifest.json
  runs/<run_id>/partitions/<partition_id>/attempts/<attempt_id>/
    metadata/balalaika.parquet
    audit/filter_summary.csv
    webdataset/<partition_id>-<sequence>.tar
    checkpoint/workspace.tar.zst
    result.json
    _SUCCESS
  runs/<run_id>/dataset/
    partitions.parquet
    webdataset-shards.json
    filter_summary.parquet
    _SUCCESS
```

Распределённый MinIO является выбором для availability, а не требованием к
throughput инференса в этой архитектуре, поскольку повторные чтения для
инференса выполняются локально. Его production-топология использует несколько
storage hosts и erasure coding:
[архитектура развёртывания MinIO](https://min.io/docs/minio/linux/operations/concepts/architecture.html).

При установке без object storage партиции можно заранее разместить на дисках
нод, а в манифесте записать peer locations. Необходимо хранить не менее двух
копий на разных машинах, иначе при сбое диска партицию будет невозможно
восстановить. Этот режим дешевле, но сложнее в эксплуатации.

Невозможно полностью избежать хотя бы однократного перемещения данных. Сейчас
настроенный датасет находится на одном локальном ext4 HDD по пути
`/mnt/hdd_6tb_1/youtube_data_incoming`. Этот диск остаётся узким местом для ingest,
пока входы не будут упакованы и перераспределены либо скопированы в
распределённый надёжный уровень. Один scheduler не может увеличить throughput
чтения одного физического диска.

### Переносимая идентичность и финализация

Надёжным ключом sample должен стать
`dataset_id + partition_id + relative_path` или другой стабильный sample ID.
Абсолютные локальные пути нод не должны служить межзапусковой идентичностью.

Каждая партиция публикует фрагмент Parquet и глобально уникальные WebDataset
shards. Кластерный finalizer проверяет все markers `_SUCCESS`, представляет
фрагменты как партиционированный Parquet dataset, агрегирует audit-записи и
записывает манифесты уровня датасета. Он не копирует всё аудио через Coordinator
и не пересобирает уже созданные tar shards.

## Доставка Docker и моделей

### Артефакты пилота в этой ветке

Первый контейнерный слой уже реализован:

- [`Dockerfile`](../Dockerfile) собирает закреплённое окружение Python 3.12/CUDA
  12.8/ORT/TRT для запуска от non-root-пользователя;
- [`.dockerignore`](../.dockerignore) исключает модели, датасеты, caches, логи,
  credentials и локальные артефакты из build context;
- [`docker/entrypoint.sh`](../docker/entrypoint.sh) предоставляет команды
  `smoke`, `warmup` и `pipeline` с корректным forwarding сигналов;
- [`docker/prepare_config.py`](../docker/prepare_config.py) формирует временный
  локальный для контейнера YAML, не изменяя смонтированный config хоста;
- [`docker/run_gpu0.sh`](../docker/run_gpu0.sh) является pilot launcher, всегда
  запрашивает физический GPU 0 и предоставляет один логический `cuda:0`;
- [`docker/smoke_test.py`](../docker/smoke_test.py) выполняет реальные проверки
  Torch CUDA, ONNX Runtime CUDA и FFmpeg/audio;
- [`docker/README.md`](../docker/README.md) содержит команды сборки и запуска.

Ручной `run_gpu0.sh` намеренно остаётся простым single-GPU smoke launcher.
Мультинодовый controller находится в [`cluster_admin`](../cluster_admin/) и
описан в [`docs/cluster_admin.md`](cluster_admin.md): для каждой ноды он принимает
ordered `gpu_devices`, фиксирует resolved GPU UUID и передаёт дочернему Balalaika
компактный набор `cuda:0..N-1`. Режим `direct` запускает `base.sh` внутри уже
существующего worker-контейнера без доступа к Docker socket.

Dockerfile проходит `hadolint`, вспомогательные скрипты проходят проверки
syntax/unit/format, а оба закреплённых digest исходных OCI-образов получены из
соответствующих registry. Текущее окружение выполнения Codex само является
непривилегированным контейнером без `CAP_SYS_ADMIN`; вложенный Docker daemon не
может монтировать слои BuildKit. Поэтому фактическую сборку образа и smoke-тест
GPU-контейнера необходимо выполнять через обычный Docker daemon хоста,
используя команды из `docker/README.md`.

### Что остаётся на каждом хосте

Требуется только небольшая первоначальная настройка хоста:

- совместимый NVIDIA driver;
- Docker Engine;
- NVIDIA Container Toolkit;
- Nomad client и NVIDIA device plugin;
- локальные каталоги cache/staging.

Эта настройка будет автоматизирована с помощью Ansible или cloud-init. Python,
FFmpeg, PyTorch, ONNX Runtime, userspace-библиотеки TensorRT и код Balalaika
находятся в OCI-образе. NVIDIA Container Toolkit предоставляет контейнеру
выделенные GPU-устройства хоста и интерфейс driver:
[архитектура NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/arch-overview.html).

Docker bind mounts относятся к файловой системе хоста, на котором работает
Docker daemon, поэтому каждая allocation должна монтировать пути, существующие
на выбранной ноде, а не пути на управляющей машине. Persistent volumes/bind
mounts обеспечивают производительность локального хоста:

- [поведение Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)
- [хранилище и volumes в Docker](https://docs.docker.com/engine/storage/volumes/)

### Содержимое образа

Образ содержит:

- Python 3.12;
- закреплённое окружение `requirements_dev.cuda128.txt`;
- wheels PyTorch 2.8, совместимые с CUDA 12;
- библиотеки ONNX Runtime GPU и TensorRT 10;
- FFmpeg и необходимые runtime-системные библиотеки;
- исходный код Balalaika с неизменяемым digest образа;
- container entrypoint и smoke tests.

Крупные файлы моделей не встраиваются в образ. Текущий локальный каталог
`models/` занимает около 5,3 ГБ и изменяется независимо от кода. Встраивание его
в каждый образ делало бы огромный слой недействительным и требовало бы его
повторной передачи при каждом изменении weight.

### Манифест и кэш моделей

Каждый запуск ссылается на неизменяемый манифест моделей:

```json
{
  "models": [
    {
      "id": "logical-model-name",
      "uri": "s3://models/path/model.onnx",
      "revision": "exact-revision-or-null",
      "sha256": "...",
      "size": 123456789
    }
  ]
}
```

Перед выполнением партиции нода загружает во временный каталог только
отсутствующие weights, проверяет SHA256 и атомарно переводит завершённый bundle
в рабочее состояние. Cache монтируется в inference-контейнер в режиме read-only.
Caches Hugging Face, Torch и onnx-asr также размещаются в persistent volume,
локальном для ноды, и после prefetch работают в offline-режиме.

Рекомендуемые каталоги ноды:

```text
/var/lib/balalaika/models
/var/lib/balalaika/trt-cache
/var/lib/balalaika/data-cache
/var/lib/balalaika/runs
```

При запуске стадии weights моделей загружаются с локального диска в каждый
процесс/GPU. Docker caching исключает повторную установку кода, а model caching
исключает загрузку из сети, однако для инференса модель всё равно необходимо
загрузить в RAM/VRAM. Поэтому партиции должны быть достаточно крупными, чтобы
стоимость этого запуска была малой.

### TensorRT и профили нод

TensorRT engines являются скомпилированными артефактами, а не переносимыми
weights модели. Храните их локально на ноде и включайте в ключ как минимум:

```text
image digest + model SHA256 + GPU model/compute capability +
driver/CUDA/ORT/TensorRT versions + optimization profile + batch settings
```

Первую сборку engine следует защищать блокировкой. Перед production необходимо
прогреть каждый hardware class. `node_profile.json` также относится к отдельному
hardware class/ноде, и его путь уже можно изменить с помощью
`BALALAIKA_NODE_PROFILE`.

## Балансировка нагрузки

«Разделить поровну» не должно означать назначить каждой ноде одинаковое число
файлов. Различаются длительности аудио, ветви моделей, доли отфильтрованных
данных, скорость дисков и скорость GPU.

Выбрана политика динамических leases:

- создавать существенно больше партиций, чем нод;
- оценивать weight по длительности аудио и исторической стоимости стадии;
- позволять свободному worker забирать следующую совместимую партицию;
- отдавать предпочтение ноде, на которой партиция уже закэширована;
- позволять быстрым нодам естественным образом завершать больше работы;
- оставлять самые маленькие партиции на конец, чтобы сократить long tail.

Внутри партиции текущие локальные GPU workers продолжают делить работу. На
уровне кластера Coordinator распределяет партиции. Это два независимых уровня
планирования.

## Leases, повторные попытки и семантика exactly-once visibility

Состояния задачи Coordinator:

```text
QUEUED -> LEASED -> RUNNING -> COMMITTING -> DONE
                                     \-> FAILED/QUARANTINED
```

Lease включает `attempt_id`, `node_id`, `lease_token`, `lease_epoch` и
`lease_until`. Worker отправляет heartbeat. После истечения lease партиция
возвращается в очередь, и новый attempt может выполняться в другом месте.

Выполнение имеет семантику at-least-once. Публикация имеет семантику
exactly-once-visible:

- каждый attempt записывает данные в уникальный prefix;
- временные результаты никогда не считаются committed;
- completion manifest содержит хеши input/config/image/model и checksums
  результатов;
- `_SUCCESS` записывается последним;
- commit использует текущие lease epoch/token;
- запоздавший worker из attempt с истёкшим lease не может заменить выбранный
  результат.

Nomad перезапускает или перемещает контейнер. Coordinator решает, допускает ли
семантика задачи retry. При сбоях ноды/сети retry выполняется с backoff. Ошибки
конфигурации и несовпадение checksums модели завершаются без слепых retries.
После исчерпания небольшого бюджета retries партиция перемещается в quarantine
для проверки.

Исходный input неизменяем. Деструктивные фильтры работают только с локальной для
attempt копией. Прежде чем checkpoint/retry на уровне стадии можно будет считать
безопасным, denoising необходимо перевести на временный файл, fsync и атомарный
rename.

## Контракт воспроизводимости

Каждый манифест запуска должен фиксировать:

- `run_id` и `dataset_id`;
- Git commit и неизменяемый digest OCI-образа;
- нормализованный хеш config;
- хеш манифеста моделей и хеши/revisions отдельных моделей;
- манифест входных партиций и checksums;
- запрошенный диапазон стадий и thresholds;
- определённую кодом версию схемы;
- hardware class и значимую информацию о TensorRT profile;
- random seeds, производные от стабильной идентичности sample, если стадия
  использует sampling.

Изменение любого из этих значений создаёт новую идентичность запуска. Старые
completion markers никогда не должны незаметно удовлетворять условиям нового
запуска.

## Безопасность и эксплуатация

- Не предоставлять сетевой доступ к Docker daemons или
  `/var/run/docker.sock`.
- Nomad clients запускают только разрешённые образы, закреплённые по digest.
- Workers получают краткоживущие credentials, ограниченные их входными и
  выходными prefixes.
- Credentials для входов имеют режим read-only; credentials для результатов не
  могут изменять исходные партиции.
- Bundles моделей монтируются read-only, а workspaces партиций — writable.
- Локальный scratch удаляется только после удалённой загрузки и проверки commit.
- В каждом манифесте результата записываются нода, GPU UUID, хеши
  image/model/config, timings, counts и ошибки.
- Метрики dashboard должны включать queued/running/failed-партиции, возраст
  lease, GPU utilization, долю попаданий в локальный cache, bandwidth
  stage-in/out и throughput каждой стадии.

## Необходимые изменения Balalaika

Изоляция партиций позволяет первому пилоту переиспользовать большую часть
существующего кода стадий. Для кластерного слоя всё ещё требуются следующие
работы.

1. Добавить закреплённый GPU Docker-образ, entrypoint, формирование config,
   cache mounts и CPU/GPU smoke tests.
2. Определить схемы run, model, partition, attempt, result и completion.
3. Добавить input packer, который группирует записи по оценочной стоимости и
   создаёт неизменяемые архивы с checksums.
4. Добавить state machine задач Coordinator и шаблоны Nomad worker jobs.
5. Добавить wrapper worker для stage-in, локального `base.sh`, валидации,
   stage-out, heartbeat и fenced commit.
6. На границах publication/merge заменить идентичность на основе абсолютного
   пути стабильными sample IDs относительно партиции.
7. Выделить для WebDataset shards namespace с `partition_id` и публиковать
   манифест шардов.
8. Публиковать Parquet как фрагменты партиций и реализовать лёгкий кластерный
   finalizer вместо одного изменяемого Parquet-файла для всего кластера.
9. Сделать запись медиафайлов в denoising и стадии 1 атомарной.
10. Публиковать результат collate через проверку временного файла и атомарный
    replace.
11. Добавить манифесты решений keep/drop для деструктивных стадий фильтрации.
12. Сделать random crops детерминированными на основе идентичности
    run/config/sample там, где placement или retry иначе могут изменить
    результаты.

## Этапы внедрения

### Фаза 0: контракты и Docker

- Собрать закреплённый образ и выполнить smoke tests на одном явно выбранном
  GPU.
- Определить манифесты, IDs, хеши, layout результатов и политику обработки
  сбоев.
- Автоматически подготовить две ноды и выполнить prefetch моделей.
- Проверить, что один и тот же небольшой локальный датасет даёт одинаковые
  результаты внутри и снаружи контейнера.

Критерии завершения: воспроизводимый контейнер, один видимый GPU, работающие
providers CUDA и ONNX Runtime, persistent caches моделей/TRT, отсутствие файлов
моделей в образе.

### Фаза 1: ручной пилот с партициями на двух нодах

- Разделить предварительно нарезанный датасет на независимые корни партиций.
- Вручную разместить партиции на локальных дисках.
- Выполнить score-only стадии 3.5, 4, 5, 6 и 7, затем стадии 8-11.
- Опубликовать Parquet/status-артефакты партиций.
- Сравнить число строк, дублирующиеся IDs, scores и checksums с эталонным
  запуском на одной ноде.

Критерии завершения: эквивалентность результатов и отсутствие записи между
партициями.

### Фаза 2: автоматизированное планирование

- Развернуть Nomad, Coordinator, PostgreSQL, registry и холодное object storage.
- Добавить динамические leases, heartbeat, предпочтение locality, stage-in/out
  и уникальные prefixes attempts.
- Инъецировать остановку контейнера, перезагрузку ноды, потерю сети, повторную
  доставку, устаревший lease и restart Coordinator.

Критерии завершения: каждая партиция либо committed ровно один раз, либо явно
переведена в quarantine; запоздавшие attempts не могут перезаписать committed
результаты.

### Фаза 3: финальные артефакты

- Выполнять collate/export отдельно для каждой партиции.
- Добавить переносимое переписывание путей и финализацию партиционированного
  Parquet.
- Выделить namespace для WebDataset shards и агрегировать данные audit/report.

Критерии завершения: один манифест датасета полностью перечисляет проверенные
фрагменты Parquet и WebDataset shards без передачи аудио через Coordinator.

### Фаза 4: деструктивные стадии и стадии с изменением данных на месте (in-place)

- Выполнять фильтры в одноразовых workspaces и публиковать решения keep/drop.
- Сделать denoising и другие записи медиафайлов атомарными.
- Добавить необязательные checkpoints workspace на границах фаз.

Критерии завершения: остановка worker во время удаления/кодирования не может
повредить надёжный input или создать видимый частичный результат.

### Фаза 5: приём исходных данных (raw ingestion) и подготовка к production

- Разделять исходные записи на партиции до стадии 1.
- Оставить стадию 0 и глобальную финализацию только на стороне controller.
- Добавить HA-серверы Nomad, резервные копии PostgreSQL, избыточность object
  storage, observability, garbage collection и ограничения capacity.

Критерии завершения: многодневные запуски переносят штатную потерю нод и
сверяют каждую входную партицию, строку, выходной shard и ошибку.

## Решения, которые ещё нужно принять до production

- Точное число нод, типы GPU, размеры локальных дисков и bandwidth сети.
- Используется ли уже Nomad/Slurm/Kubernetes в целевом окружении.
- Выбор надёжного уровня: существующий S3/Ceph, standalone MinIO,
  distributed MinIO или предварительно реплицированные локальные партиции.
- Требуемый срок хранения исходных входов, checkpoints, неудачных attempts и
  логов.
- Максимально допустимая длительность retry партиции.
- Используют ли фильтры фиксированные thresholds или требуют глобальный
  двухпроходный threshold.
- Принимают ли конечные потребители партиционированный Parquet dataset или им
  требуется материализованный единый файл.
- Требования к authentication, secrets, registry и сетевой изоляции.

## Текущий вывод

Multi-node Balalaika реализуема, и большинство циклов инференса не требуется
переписывать. Надёжной границей является изолированная партиция датасета, а не
отдельный аудиофайл в общей файловой системе. Docker обеспечивает
воспроизводимую доставку runtime; Nomad управляет жизненным циклом
host/GPU/container; Coordinator управляет специфичными для Balalaika очередью,
barriers, leases и публикацией; локальный staging убирает общую файловую систему
из hot path инференса.

Первой целью реализации является Docker-пилот на двух нодах с неизменяемыми
партициями, локальными caches моделей/данных, одним явно выбранным GPU на каждый
smoke test и score-only стадиями до включения деструктивной обработки.
